## 先给结论

技术文档最大的浪费是：读者读了两屏才发现这不是他要找的东西。所以第一段就写结论——做了什么、结果如何、代价是什么。

## 结构优于文采

一个稳定的骨架：

1. 结论（一句话）
2. 背景（为什么需要做这件事）
3. 方案（做了什么，关键取舍）
4. 证据（数据、对比表、失败案例）
5. 边界（什么情况下不适用）

## 能用表格就不用段落

对比三件事时，横排的表格永远比三段话更快被理解。同理，流程用编号列表，层级用标题，别用缩进和加粗硬凹结构。

## 少用形容词

"大幅提升""显著优化"没有信息量。改成"p99 从 820ms 降到 240ms"，读者立刻知道值不值得继续读。

> 一个可执行的检验：把所有形容词删掉，段落是否还有信息？如果没有，说明本来就没写清楚。

## 代码块要能跑

贴代码时保留必要上下文（import、类型），省略无关部分并明确标注。半截代码比不贴代码更浪费时间。

```ts
// 省略了日志与错误处理
const port = createDbPort(config.db)
await migrate(port.db)
```

## 承认不知道的部分

写清楚"这部分没验证""只在特定条件下成立"，比假装完备更可信。技术读者的信任来自边界清晰，而不是语气笃定。

## 写给自己看

半年后的你就是目标读者。当时觉得显而易见的上下文，那时一定已经忘了——这正是要写下来的原因。
