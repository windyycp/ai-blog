## 先说结论

RAG 的成败几乎不由模型决定。同样的模型，检索质量从 60% 提到 90%，回答可用率会翻倍；反过来，把模型从 7B 换成 70B，召回不变的情况下提升有限。

所以先把预算花在检索链路上。

## 第一坎：切分不是按字符数切

固定 512 字符切分会把定义和解释切到两个块里，检索到任何一个都不完整。可行的做法：

- 按语义边界切（标题、段落、列表项），再合并到 300~800 字符
- 每个块带上父级标题路径，作为检索时的上下文前缀
- 相邻块保留 15% 重叠，避免边界信息丢失

## 第二坎：召回不等于相关

向量召回擅长语义相似，不擅长精确匹配。产品名、错误码、函数名这类 token，向量经常召不回来。

> 混合检索不是加分项，是必需项：BM25 + 向量，用 RRF 融合。

```ts
const fused = rrf([bm25Results, vectorResults], { k: 60 })
```

## 第三坎：重排比换模型便宜

初步召回 50 条，用 cross-encoder 重排到 8 条，效果通常比直接扩大召回窗口更好，成本只有一次小模型推理。

## 第四坎：评测集必须手写

自动指标（BLEU、ROUGE）在问答场景几乎无效。现实做法是攒 100 条真实问题，人工标注「哪些文档应该被召回」，先算 Recall@k，再算回答正确率。

| 指标 | 目标 | 说明 |
| --- | --- | --- |
| Recall@8 | > 0.9 | 检索层质量 |
| 引用准确率 | > 0.95 | 回答里的引用是否真的支撑结论 |
| 拒答率 | 10% 左右 | 无答案时应该拒答 |

## 第五坎：上下文窗口不是越大越好

把 20 个块塞进 100k 上下文，模型会开始忽略中间部分（lost in the middle）。8 个高质量块，比 20 个凑数块更稳。

## 第六坎：上线后要能定位问题

把「检索到的块 id + 重排分数 + 最终 prompt」全量落日志。出问题时先看是召回错了，还是模型没用召回内容，这两类问题的修法完全不同。
