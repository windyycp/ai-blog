## ISR 的三层时间尺度

同一个站点里，不同页面的数据新鲜度要求差得很远：

| 页面 | revalidate | 理由 |
| --- | --- | --- |
| 首页 | 60s | 新文章需要尽快露出 |
| 列表 | 60s | 同上 |
| 详情 | 300s | 正文几乎不变 |
| 归档 | 300s | 聚合数据，慢一点无感 |
| 关于 | 600s | 手工写的静态内容 |

统一设一个值，不是太慢就是浪费。

## cache tag 决定失效粒度

只靠时间窗，最多延迟几分钟。要精确失效，必须给每次取数打 tag：

```ts
const res = await fetch(`${API}/posts/${slug}`, {
  next: { revalidate: 300, tags: [CACHE_TAGS.post(slug), CACHE_TAGS.list] },
})
```

发布一篇文章时，只需要失效 `list` 和这篇的 `post:{slug}`，其余页面缓存全部保留。

## 采集系统不会通知你

本站的内容由外部采集系统直接写库，`api` 感知不到"发布"事件。三道保险：

1. **被动兜底**：定时比对 `max(updated_at)`，变化才触发失效
2. **主动通知**：采集完成后调内部接口，带 token
3. **时间窗**：所有 ISR 自然过期

只有第三道是"一定有效"的，前两道是延迟优化。设计时不要把前两道当成一致性保证。

## 静态与动态的边界

详情页要记录浏览量，于是每次访问都要写库。这会强制页面变成动态渲染，ISR 就废了。

解法：正文保持静态，浏览量由一个 client 组件在挂载后 `POST` 上报。代价是首次打开时数字可能旧几秒，收益是整页可缓存。

## 一个常踩的坑

`fetch` 默认会缓存 GET 请求，但在 Route Handler 里如果不显式声明，行为可能和 Server Component 不一致。统一在封装层里写死 `cache` 与 `next` 选项，别在每个调用点单独判断。
