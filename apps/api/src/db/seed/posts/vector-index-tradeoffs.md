## 三种索引，三种经济性

选型时不要问"哪个最好"，要问"我能不能接受这个代价"。

| 索引 | 召回 | 内存 | 构建 | 适用 |
| --- | --- | --- | --- | --- |
| Flat（暴力） | 100% | 低 | 无 | < 10 万条，或作为评测基线 |
| IVF-Flat | 高（需调 nprobe） | 中 | 需要训练 | 百万级，批量写入 |
| HNSW | 很高 | 高（图结构常驻） | 慢 | 在线服务，低时延 |
| PQ / 量化 | 中 | 很低 | 中 | 内存受限，可接受精度损失 |

## HNSW 的真正成本

图结构的内存占用大约是原始向量的 1.2~1.5 倍。100 万条 1536 维 float32 向量本身约 6GB，加上图，轻松超过 8GB。

如果预算有限，先降维（或用二进制量化），再考虑 HNSW。顺序反了会很痛苦。

## 过滤条件是大坑

带 `WHERE` 的向量检索，两种实现方式：

1. **先过滤再检索**：召回窗口足够大时准确，窗口小了会漏
2. **先检索再过滤**：可能返回不足 k 条，需要重试放大

多数数据库选第二种，然后在 UI 上表现为"结果页只有三条"。生产环境要么显式放大 `ef_search`，要么把过滤字段做成分区。

## 评测必须固定参数

换索引前后对比，必须锁死同一批查询、同一个 top-k、同一个 embedding 模型。否则数字没有意义。

```ts
const report = await evaluate({
  queries: goldenSet,
  k: 10,
  metric: 'recall@10',
})
```

## 什么时候根本不需要向量库

语料少于几千条时，把 embedding 加载进内存做暴力检索，延迟通常远低于一次网络往返。先用 Flat 跑起来，等数据量真的成为瓶颈再迁移，能省掉大量运维工作。
