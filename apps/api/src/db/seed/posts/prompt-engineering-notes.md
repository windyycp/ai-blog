## 把 prompt 当代码

散落在代码字符串里的 prompt 是最常见的债。至少要做到：

1. 独立文件，纳入版本控制
2. 有唯一 id 和版本号，日志里记录用的是哪一版
3. 改动必须过评测集

## 结构比措辞重要

同一段 prompt，调换顺序带来的差异经常大于换同义词。稳定的结构：

- 角色与边界（你能做什么、不能做什么）
- 输入格式（明确标注分隔符）
- 输出格式（给出 schema，而不是"用 JSON 回答"）
- 少量示例（2~3 个足够，多了反而过拟合）

## 输出必须是可解析的

要求模型返回 JSON 时，最好用结构化输出能力（response_format / tool call），而不是靠 prompt 里写"只返回 JSON"。后者在长输入下失败率明显更高。

```json
{
  "answer": "string",
  "citations": ["chunk_id"],
  "confidence": 0.0
}
```

`confidence` 字段即使不准，也能作为兜底阈值的抓手。

## 评测集从小开始

50 条真实用例就能发现 80% 的回归。关键是：

- 用例来自线上日志，不是自己编的
- 每条有明确的通过标准（可自动判定优先）
- 改动前后各跑一次，记录 diff

## 不要用 prompt 修模型缺陷

模型不会算术，就用工具；模型不知道实时信息，就检索。用 prompt 硬掰，短期能过，长期一定在边界 case 上崩。

## 灰度与回滚

新 prompt 先给 10% 流量，对比两组的通过率和平均 token 消耗。token 消耗常常是容易被忽略的指标——一个"更严谨"的 prompt 可能贵三倍。
